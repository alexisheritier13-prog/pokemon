# Story 1.5: Projet Supabase et schéma de base

## Status
Review

## Story
**As a** développeur,
**I want** un schéma de base versionné, sécurisé par RLS et testable en local,
**so that** les données sont protégées dès la première ligne.

## Acceptance Criteria
1. La CLI Supabase est configurée pour un environnement local. Les migrations versionnées activent PostGIS et créent `profiles`, `user_settings` (zone arrondie à ~1 km par trigger), `alert_preferences`, `games`, `brands`, `products`, `stores` (avec `location geography(Point)`, `osm_ref` unique, statut de validation) et `store_favorites`, ainsi que la configuration `private.app_config`.
2. La RLS est activée sur chaque table : lecture publique des magasins validés et des produits actifs, écriture limitée à ses propres données, et opérations admin réservées à un rôle.
3. Les types TypeScript sont générés depuis le schéma.
4. Des tests d'intégration vérifient les policies (anonyme, utilisateur, autre utilisateur, admin).
5. Une **requête de recherche par rayon** (magasins à moins de X km d'un point) existe et est testée.
6. Le workflow CI d'intégration (`supabase start` → migrations → tests Vitest d'intégration → contrôle que les types générés sont à jour) tourne sur chaque push.

## Dev Notes
- Schéma de référence : [Source: architecture/database-schema.md]. La numérotation logique 0001 à 0013 est découpée en migrations par story (note PO). Ici : 0001 à 0004, plus la RLS associée et `client_errors`.
- `alter default privileges … revoke execute … from public, anon` : chaque RPC reçoit un `grant` explicite.
- Colonnes de `profiles` : `banned_at` n'est jamais lisible, et seuls `pseudo` et `avatar_key` sont modifiables par l'utilisateur (droits par colonne).

### Testing
- `npm run db:start` puis `npm run test:int`. Les tests refusent de tourner contre une URL non locale.
- Les comptes de test sont créés via l'API admin locale, avec des mots de passe aléatoires générés dans le test.
