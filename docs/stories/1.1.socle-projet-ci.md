# Story 1.1: Socle projet et intégration continue

## Status
Review

## Story
**As a** porteur de projet,
**I want** un projet Vite + React + TypeScript outillé et déployé automatiquement,
**so that** chaque changement est vérifié et visible en ligne sans manipulation.

## Acceptance Criteria
1. Le projet est initialisé avec Vite, React, TypeScript strict, Tailwind, React Router et TanStack Query, plus ESLint, Prettier et Vitest configurés et passants.
2. Le nom de l'app vient d'une **config unique** (`APP_NAME` et dérivés) utilisée par l'UI et le manifest.
3. Une CI (GitHub Actions) exécute sur chaque push : lint, typecheck, tests, build, puis un **contrôle du budget de bundle initial < 200 ko gzip** qui fait échouer le build en cas de dépassement.
4. Le front est déployé automatiquement sur l'hébergeur retenu (Vercel), et une page canari affiche le nom de l'app et la version.
5. Un `.env.example` documenté liste toutes les variables attendues.
6. Le footer contient la mention de non-affiliation.

## Dev Notes

### Contexte
Première story du projet. Aucun code n'existe encore. Le dépôt contient seulement la documentation BMAD (`docs/`), `.bmad-core/` et `.claude/`. Ne jamais modifier `.bmad-core/`.

### Stack et versions
[Source: architecture/tech-stack.md]
- React 19, Vite (dernière majeure stable), TypeScript 5 strict, **Tailwind v4** (décision D1 : tokens via `@theme` en CSS, pas de `tailwind.config.js`), React Router 7 (data router), TanStack Query 5, Zustand 5, Zod 4, `@phosphor-icons/react` 2.
- Lint et format : ESLint 9 (flat config) + Prettier 3. Tests : Vitest + Testing Library. Budget : `size-limit` 11.
- Versions **épinglées** (`package-lock.json` commité) : prendre la dernière version stable de la majeure indiquée.

### Structure à respecter
[Source: architecture/source-tree.md, architecture/frontend-architecture.md]
```text
src/
├── app/ (App.tsx, router.tsx, providers.tsx)
├── config/ (app.ts, env.ts)
├── copy/fr.ts
└── main.tsx
.github/workflows/ci.yml
vercel.json  .env.example  .nvmrc  eslint.config.js  .prettierrc  vitest.config.ts
```
Ne pas créer à l'avance les dossiers des stories suivantes (`features/`, `sw/`, `design/`…).

### Règles critiques applicables
[Source: architecture/coding-standards.md]
- Variables d'env lues **uniquement** via `src/config/env.ts` (Zod).
- **Aucun texte en dur** dans les composants : tout passe par `src/copy/fr.ts`.
- Aucune couleur ni taille littérale « de design ». Comme les tokens n'existent pas encore, utiliser les utilitaires Tailwind neutres par défaut pour la page canari, qui sera restylée en story 1.2.
- Le nom de l'app n'apparaît **nulle part** en dur ailleurs que dans `src/config/app.ts` (NFR13).
- La marque Pokémon n'est citée que de façon descriptive (NFR8).

### Hébergement
[Source: architecture/deployment-architecture.md]
- Vercel (D2), intégration Git : preview par PR, production sur `main`. Build `npm run build`, sortie `dist`.

### Actions du porteur (à lister en fin de story)
1. Créer le dépôt GitHub (privé conseillé) et pousser `main`.
2. Créer le projet Vercel lié au dépôt (framework Vite, build `npm run build`, sortie `dist`).
3. Vérifier que la CI GitHub Actions passe au vert et que l'URL Vercel affiche la page canari.

### Testing
[Source: architecture/testing-strategy.md]
- Tests colocalisés `src/**/*.test.ts(x)`, Vitest + jsdom.
- Tests minimaux de cette story : `app.ts` expose un nom non vide et une version semver ; la page canari affiche `APP_NAME` et la mention de non-affiliation (Testing Library).
- Avant de passer en « Review » : `npm run lint`, `npm run typecheck`, `npm run test -- --run`, `npm run build` et `npm run size` passent.
